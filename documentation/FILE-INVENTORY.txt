WORDPRESS SENTINEL — OPTIONAL FILE INVENTORY

Upload the package into compat/wp-sentinel while no operation runs. Preserve
profiles, reference ZIPs, reviews, reports and recovery stores. Existing commands
work without the new switch. No remediation is automated.

First test disposable fixtures on the host:

python3 -I -S test_file_inventory.py

Seven tests use temporary fake sites only. These test added/changed/missing files,
exclusions, count and size limits, mocked permission failures, interrupted reads,
wrong-site/reversed input rejection and the command-line round trip. They do not
read or change the real site. This is not a power-loss or hostile-race test.

Create the first inventory using your profile:

python3 -I -S sentinelctl.py --profile ../site.json scan --file-inventory

Repeat the same command for a second inventory. Do not deliberately edit the
live website to test this: disposable tests already cover those changes.
Each new report-* directory includes file-inventory.json. Preserve both folders.
Other scan switches such as --core --database --plugins --persistence and
--account-cron remain opt-in. This command alone runs file and saved-reference
checks; it does not refresh database or startup checks.

Compare two sequential inventories (replace EARLIER and LATER with actual names):

python3 -I -S sentinelctl.py --profile ../site.json file-changes --before ../report-EARLIER/file-inventory.json --after ../report-LATER/file-inventory.json

A new file-changes-* folder receives file-changes.json and file-changes.html.
The comparison is offline and does not connect to the website or database.

ADDED: a hashed file appeared after a completed earlier traversal that did not
observe the path. This is an observation between scans, not proof of creation time.
CHANGED: both reads succeeded but SHA-256 or byte size differs.
MISSING: a previously hashed path was not observed in a completed later traversal.
UNCHANGED: both reads succeeded and hash/size match; this does not imply benign.
UNKNOWN: an exclusion, size limit, inaccessible/changed file, type change, symlink
or incomplete traversal prevents a reliable content comparison. An unchanged
excluded configuration file will still be unknown. Directory/type observations
may also appear here. Directory traversal failures, skipped symlink directories
and count limits conservatively prevent missing/added conclusions across the
affected inventory, even for unrelated paths.

The inventory hashes the same bytes read during the scanner's file pass. It
records relative paths, sizes, SHA-256, read/skip states, scan times and limits,
not file contents. wp-config.php and .env files are now hashed; their contents are never saved. Reports can expose
private filenames, so retain them outside all public document roots.

Publishing uses a temporary JSON file followed by replacement of the final
filename after flushing the file. Interrupted scans do not publish a completed
inventory. An interruption while saving may leave file-inventory.json.tmp;
do not rename it to bypass validation. Run a new scan into a new output folder.
The inventory is published after the file pass, before optional checks; it may
exist even if a later database/network check fails. Read coverage in both files.

This is not an atomic filesystem snapshot: live writers can change paths during
or after traversal, and hostile same-account races are not fully prevented.
Permission tests inject failures; actual hosting permissions may behave differently.
Hash files are not authenticated against same-account tampering. Retain independent
off-account evidence if integrity against compromise is required. No contents
can be restored from a hash inventory. Keep real backups.

Old reports without inventories cannot supply retrospective file hashes. The
first inventory is an observed baseline, not a claim that every file is clean.
Existing finding reviews remain separate from file-inventory comparisons.

0.15.1 REPORTING UPDATE
Added and missing directories are listed separately as directories_added and
directories_missing in JSON and HTML. File counts retain their previous meaning.
Unchanged directories are omitted. Type changes, symlinks and exclusions remain
unknown; absence in an incomplete traversal never confirms an addition/removal.
Existing inventories work unchanged. Re-run file-changes to create a new report;
previous reports are retained. No website scan is needed to recompare inventories.

0.18 UPDATE
A skipped symlink or unreadable directory now only prevents added/missing conclusions
for paths inside it; a file limit still affects the whole inventory. Older inventories
keep the earlier all-or-nothing behaviour. The new fields are uninspected_directories,
file_limit_reached and traversal_scope_known.

PERMISSIONS, OWNERS AND DATES
Each inventory entry now also records its modified time (mtime_utc) and, on Linux
hosts, its permissions (mode, such as 0644), owner (uid, gid) and status-change time
(ctime_utc). owner_names maps each uid to its account name. metadata_fields lists
what was recorded. Times are UTC and taken from the same file reads as the hashes.

The unchanged group lists paths only, as plain strings, to keep comparisons small;
both inventories still hold every unchanged file's hash, size and dates. Comparisons
made before this update listed full entries there too.

file-changes adds a permissions_changed group: entries whose mode or owner differ
between the two inventories, whether or not the content changed. It is listed
alongside the content result, so a file can appear in both. Inventories made before
this update have no permissions, so they never produce this group.

Build a timeline from one inventory:

python3 -I -S sentinelctl.py --profile ../site.json timeline --inventory ../report-LATER/file-inventory.json

Add --since 2026-10-01 to list only entries modified or changed from that date, and
--limit 2000 for longer tables in the page. A new timeline-* folder receives
timeline.json and timeline.html. sentinel-remote.py builds both automatically in each
run folder. timeline.json keeps the newest 5,000 entries; file-inventory.json still
has every entry.

The page shows activity by day, so a burst of writes on one day stands out, bulk
changes, the most recent entries, and flags. A bulk change is when more than 20 older
files had their status changed within a minute of each other, such as a WordPress
update, a restore, a migration or a bulk chmod. Each is listed once with its time
span and size; check it matches something you or your host did. Files changed on
their own are flagged:

world-writable       Any account on the server can change it.
setuid-or-setgid     Runs with its owner's or group's rights. Rare in a website.
other-owner          Owned by a different account from most of the site, such as
                     the web server writing files itself.
ctime-after-mtime    Status changed more than a day after the content was dated, and
                     not as part of a bulk change. Usually a chmod, or one file
                     copied with its old date. It is also what setting a file's
                     date back looks like.
future-dated         Modified after the scan: set by hand, or a clock is wrong.

Flags are prompts for review, not findings, and do not change the report's priority
counts. Flagged entries are listed whatever --since says. Anyone who can write a file
can also set its modified time, but not its status-change time, so compare both. A
quiet timeline is not proof that nothing changed, and an attacker who changes many
files at once lands in a bulk change, not in the flags. Timelines from inventories
made before this update say so and stay empty.
