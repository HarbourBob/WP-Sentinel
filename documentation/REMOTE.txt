WORDPRESS SENTINEL 0.25.0-rc1 — RUNNING FROM YOUR OWN COMPUTER

sentinel-remote.py runs on your computer. It connects with ssh, uploads the scanner
to a temporary folder on the host, runs it, copies the evidence back, removes the
temporary folder, and compares the new file inventory with earlier runs held on your
computer. Nothing stays installed on the host.

WHY

Anything stored on a hosting account can be altered by an attacker running as that
account, including earlier reports and baselines. Evidence held on your computer
cannot be, so a later comparison starts from something the host could not rewrite.

REQUIREMENTS

Your computer: Python 3.8 or later and an ssh client. Key-based SSH is recommended:
without a key or agent you will be asked for your passphrase at each step.
The host: Python 3.7 or later, plus PHP CLI with mysqli for --database.

RUN A SCAN

python sentinel-remote.py scan --host user@example.com --root /home/user/public_html --core --plugins --persistence

Add --database to check the database. You are prompted for the details in your
terminal over the SSH connection, and they are not stored. To avoid the prompt, use
--db-from-wp-config (see MONITORING.txt). Other options match
sentinelctl: --account-cron, --max-file-mb, --max-files, --db-row-limit,
--db-value-limit, --php, --fail-on and --locale. Use --port, --identity,
--ssh-command and --remote-python if your connection needs them.

--core reads the installed version from the site unless you give --core-version, and
its language edition, such as en_GB, unless you give --locale.

The temporary folder is created in your home folder on the host. If that folder is
inside a website, use --remote-temp to choose one that is not.

--reference plugin:folder=LOCAL.zip uploads a trusted ZIP for that run only.

--themes compares each theme with its WordPress.org copy. Themes with no public copy
are marked unverified.

WHAT YOU GET

sentinel-evidence/HOST-ID/RUN/ on your computer, one folder per run:

  report.html, report.json   The report.
  file-inventory.json        File hashes from this run.
  file-changes.json          Changes since the previous run, when there is one.
  timeline.html, .json       File dates, permissions and owners. See FILE-INVENTORY.txt.
  vulnerabilities.html, .json  Known vulnerabilities in installed versions, when an
                             API key or cached feed is available. See VULNERABILITIES.txt.

After an incident, build a checklist from a run. See CHECKLIST.txt:

python sentinel-remote.py checklist --run sentinel-evidence/SITE/RUN
  EVIDENCE.json              A hash of each file, linked to the previous run.

chain.json links the runs in order. Check that nothing has changed with:

python sentinel-remote.py verify

Exit codes for scan are those of the scanner, listed in RULES.txt. For verify: 0 all
match, 1 something differs, 2 no evidence found.

verify also lists run folders that chain.json does not cover:
- "never sealed": a scan that stopped early. prune removes old ones.
- "sealed, but not in any chain file here": the run has its own EVIDENCE.json but no
  chain lists it. This happens when two copies of the evidence folder are merged and
  one chain.json replaces the other. Its files are still checked against its own
  EVIDENCE.json, but nothing proves that record is the original. If you still have the
  other chain.json, copy it into the site's folder under a new name starting chain-,
  such as chain-2026-11-02.json, and verify checks those runs against it too. Never
  overwrite chain.json with it. prune never removes these runs.
These are listed as gaps, not problems, so they do not change the exit code.

LIMITS: WHAT THIS DOES NOT PROVE

- A compromised host can still lie. It controls the python3 that runs the scan and
  could return false results. Comparing uploaded file hashes catches simple tampering
  only, because the host reports those hashes too. This reduces the risk of tampered
  evidence; it does not remove the risk of a dishonest scan.
- For high confidence, also scan a backup copy on a machine you trust.
- The chain shows evidence is unchanged since it reached your computer. It is not a
  signature: someone able to edit your computer's files could rebuild it. Keep the
  folder somewhere backed up.
- Database passwords typed at the prompt pass through the host, as with any SSH
  session. Rotate credentials after an incident.
- Copied reports hold file paths, record identifiers and login names. Keep them private.
- Evidence sent back is treated as untrusted: only plain files with simple names are
  accepted, up to 50 files and 1 GiB.

REVIEWS AND THE REPORT PAGE

After each scan, report.html is built on this computer from the sealed report.json and
kept in SITE/views/RUN.html, which the scan prints. The host's own report.html is kept
in the run folder as received. To rebuild a run's page, for example after a review:

   python sentinel-remote.py report --run sentinel-evidence/SITE/RUN

To record that you checked a finding and it is harmless, use its number and SHA-256 from
the report:

   python sentinel-remote.py review --run sentinel-evidence/SITE/RUN --finding 3 --sha256 HASH --note "SiteGround Security folder protection"

Add --decision withdraw to cancel a review. Records are kept in SITE/review-notes, in the
same format as a hosted install's. A review covers one finding at one exact file hash:
the report counts it apart, quarantine-plan and replace-plan leave it out, and it lapses
as soon as the file changes. Database findings cannot be reviewed.

QUARANTINE FROM YOUR OWN COMPUTER

Moving files out has to happen on the host, where the files are, and the moved files
are kept there, in a private folder outside the website: wp-sentinel-private in your
home folder, or --private-dir. As with a scan, the programs are uploaded for each step
and removed afterwards. The list and its receipt are copied back here, into a
quarantine folder beside the site's runs. Every file still goes through the checks in
QUARANTINE.txt and BATCH-QUARANTINE.txt, which apply here too. sentinel-app.py does
the same from a window; see APP.txt.

1. Make a list from a saved scan. This changes nothing on the website.

   python sentinel-remote.py quarantine-plan --host user@example.com --root /home/user/public_html --run sentinel-evidence/SITE/RUN

   --priority medium or review adds lower priorities; high is the default.
   --include-critical allows files WordPress needs. The scan must be sealed and
   unchanged since. The command prints the list's folder.

2. Read plan.txt in that folder. To spare a file, start its line with #. Then check:

   python sentinel-remote.py quarantine --host user@example.com --root /home/user/public_html --plan LIST-FOLDER

   This prints the list's SHA-256. Editing the list changes it, so check again.

3. Move the files. This changes the website:

   python sentinel-remote.py quarantine ... --plan LIST-FOLDER --apply --plan-sha256 HASH

   --limit 50 moves at most 50 files; check and run again for the rest.
   --skip-problems leaves files that differ from the list where they are.

To put files back, use restore the same way: without --apply it checks, and --only,
repeatable, puts back just those files.

   python sentinel-remote.py restore ... --plan LIST-FOLDER --only wp-content/some/file.php

Keep wp-sentinel-private on the host: restore needs the list and the moved files there.

CLEAN COPIES FROM YOUR OWN COMPUTER

The same steps swap changed core, plugin and theme files for verified clean copies, and
change them back. CLEAN-REPLACEMENT.txt explains where the copies come from and what is
left out. The copies are downloaded and checked on the host, so it needs to reach
api.wordpress.org and downloads.wordpress.org. They stay in wp-sentinel-private there.

   python sentinel-remote.py replace-plan --host user@example.com --root /home/user/public_html --run sentinel-evidence/SITE/RUN
   python sentinel-remote.py replace ... --plan LIST-FOLDER
   python sentinel-remote.py replace ... --plan LIST-FOLDER --apply --plan-sha256 HASH
   python sentinel-remote.py replace-undo ... --plan LIST-FOLDER

Scan with --core, --plugins and --themes first, so the report names the changed files.
The WordPress version and language edition are read from the site; --core-version and
--locale set them instead. Read the "Clean copies from" lines replace-plan prints: is
each one the release you expect? Lists are kept in a clean-copies folder beside the
site's runs. Premium plugins and themes have no public copy and are left out.

A hosted install (INSTALL.txt) is still needed for single-file quarantine by ID, your
own ZIPs as clean copies, and database changes. The commands shown in a remote report apply to that
hosted install, with your profile, such as ../site.json, in place of PROFILE, and report
paths must be on the host for the review command.

IF IT WILL NOT CONNECT

Run this on your own computer, not in an SSH session on the host. A prompt mentioning
a path such as /home/customer/.ssh means it is running on the host, which then has to
log in to itself and keeps the evidence where an attacker could alter it.

Many hosts use a port other than 22. If ssh says a key is "known by the following
other names" with a port in brackets, such as [host]:18765, add that port:

python sentinel-remote.py discover --host user@example.com --port 18765 --identity PATH-TO-PRIVATE-KEY

Test the login on its own first. This should print the host's folder and nothing else:

ssh -p 18765 -i PATH-TO-PRIVATE-KEY user@example.com pwd

RUN AS ADMINISTRATOR

On Windows, use a normal PowerShell window, not one opened with "Run as administrator".
Evidence folders made from an administrator window belong to the Administrators group,
so your normal account and your browser cannot open them: reports show as blank pages,
and verify says access is denied. Sentinel warns when it is started that way.

To unlock folders already made, run this once from an administrator window, in the
folder holding sentinel-evidence, then go back to a normal window:

icacls sentinel-evidence /grant "${env:USERNAME}:(OI)(CI)F" /T
